# AI Mobile — M0 Readiness Audit (390px)

> Status: v1.0
> Date: 2026-07-07
> Method: read-only audit, 3 parallel slices, target width 390px (iPhone). Audited against `docs/ai-mobile/design.md`.
> Scope: `packages/web-core`, `packages/remote-web`, `packages/local-web`, `packages/ui`.

This is the M0 deliverable: a map of what already works on a phone, and the concrete
gap list that becomes the **M1 backlog**. Every finding carries `file:line` evidence.

---

## 0. Executive summary

The app is **already ~2/3 mobile-adapted**. The whole navigation shell, host/workspace
lists, the workspace three-column layout (collapses to tabs), kanban cards/filter bar,
preview browser, settings modal, diff defaults and log-body wrapping all have working
mobile branches driven by `useIsMobile` (see §2). This is a "close the gaps" job, not a
rebuild.

The real MVP blockers are **narrow and concrete**:

- **2 × P0** (block a design §10 acceptance criterion):
  1. **Approvals are not reachable** — the permission-approval UI is an inline card inside
     the scrolling transcript, not a fixed/bottom-anchored banner. Approving requires
     scrolling to find it.
  2. **Keyboard occlusion** — the `fixed inset-0` app shell doesn't shrink for the iOS
     software keyboard, so the composer *and* the approve/deny buttons get covered.
- **~5 × P1**: kanban board still renders desktop horizontal columns on phones; the
  `Dialog` primitive has no max-height/scroll (git dialogs clip off-screen); the Logs tab
  loses search/process-picker on mobile; primary actions + diff wrap/mode controls are
  unreachable on mobile; sub-40px tap targets across the navbar.
- **The rest is P2 polish** (padding, header truncation, bottom-sheet primitive, dropdown density).

**Two architecture decisions are resolved by the evidence** (details §4, §6):

- **Routing = responsive root routes.** The codebase already adapts *existing* routes in
  place (`SharedAppLayout`, `RemoteAppShell`, `WorkspacesLayout` all branch on
  `useIsMobile`). There is no `/m` tree and no reason to add one. → answers design §11 Q2.
- **Unify mobile detection.** Three thresholds coexist (`useIsMobile` = 767px viewport,
  Tailwind `md:` = 768px, tab labels = 480px) *plus* a UA-based `isRealMobileDevice()`.
  A 390px desktop window and a real phone diverge. This should be unified early in M1.

Three read-only audit slices ran in parallel, each returning `file:line`-cited findings

### 3.7 Cross-cutting cleanups

- **G18 — Unify mobile detection (P1, architectural).** `useIsMobile` = 767px viewport,
  `isRealMobileDevice()` = UA, tab labels = 480px, Tailwind `md:` = 768px. A 390px desktop
  window hits the tabbed layout but still shows the desktop ContextBar/navbar. Pick one
  viewport-based source of truth for layout; reserve UA only for true device capabilities.
  Owner: `web-core/src/shared/hooks/useIsMobile.ts` + consumers in G10.

## 4. Prioritized M1 plan

Suggested build order (grouped into coherent workstreams, ordered by acceptance-criteria risk):

**Wave A — unblock the two P0s (a small, high-leverage shell change):**
1. **G4** keyboard-aware shell (`visualViewport` → shell height). Unblocks composer + approvals on iOS.
2. **G1** bottom-anchored approval banner (data flag `hasPendingApproval` already exists).
3. **G2** ≥44px labeled approve/deny targets.

**Wave B — the core read/act surfaces (P1):**

5. **G10 + G11** mobile action row + reachable diff wrap/mode; default `wrapText:true` on mobile.
6. **G9** Logs tab process-picker + search.
7. **G6** single-column / segmented kanban board (or List-view default on mobile).

**Wave C — polish (P2):** G3, G5, G7, G8, G13, G14, G16, G17.

`Navbar.tsx`, `SharedAppLayout.tsx`/`RemoteAppShell.tsx`, `Dialog.tsx`,

## 5. Design-doc open questions (§11) — evidence-based recommendations

1. **QR pairing in M1?** — No. Keep M1 to on-screen usability; the existing pairing-code
   flow works. QR → M2 (design §5.3). M1 has no pairing gaps in this audit.
2. **Canonical mobile route (responsive root / `/m` / dedicated entry)?** — **Responsive
   root routes.** The codebase already adapts existing routes in place everywhere
   (`SharedAppLayout`, `RemoteAppShell`, `WorkspacesLayout`, kanban). A `/m` tree would
   fork maintenance for zero benefit. *Decision recommended: close this question as
   "responsive root routes".*
3. **Self-hosted relay default vs advanced?** — Out of M1 scope (transport works via
   existing relay/WebRTC). Revisit in M2.
4. **First notification channel?** — None in M1. Evaluate Web Push in M3 (design §9 M3).
5. **Mandatory surfaces for first release?** — Board, session chat + follow-up, **approvals**,
   diff (read), logs (read). Files/git/workflow-runs are secondary. Approvals + composer
   are the acceptance-criteria-critical pair (the two P0s live here).
